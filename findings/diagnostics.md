# 诊断类覆盖（D 层）：边饱和之后更敏感的 fitness

日期 2026-11-11。动机：边覆盖已经饱和（3,885 次执行 0 新边），需要一把更细的尺子
量"typer 走到了多深"。自创指标，文献里没有直接对应工作。

## 定义

一次编译产出的**诊断类**：

```
class(in) = { (E-code, normalized message) | 该诊断是 error (E3xxx 解析 / E4xxx 分析) }
```

归一化 `harness/diag.py`：

1. 丢弃所有 `Warning`（E0xxx）——它们带函数名，会把类数撑成"每改一个名字就新类"；
2. `path:line:col` → `<loc>`；
3. 引号内容保留前 40 字符（**故意保留类型名**，这样 `Expr Type Mismatch` 的
   "哪个类型对不上哪个类型"才是类的一部分；丢掉就退化成"又一条类型错误"）；
4. 数字 → `<n>`；
5. 一个输入取前 3 条唯一诊断拼成类。

语料的诊断类 = 每输入类集合的并集。**新类率** = 新增类数 / 执行次数，直接当
fitness（产生新类 ⇒ 值得变异/保留）。

## 基线数字（core 真程序，300 个输入）

| 语料 | 可编译率 | 诊断类 |
|---|---:|---:|
| 原始真程序 | 43.7% | **161** |
| 函数体变异后（同 300 个种子） | 40.3% | **174** |
| 变异带来的新类 | — | **29 / 300 execs = 0.10 /exec** |

即 1,000 次变异 ≈ 97 个新诊断类；而边覆盖在同样量级上早已 0 新增。
第一版据此说"灵敏度差两三个数量级"，**这是过度解读，撤回**。拆开这 29 个新类：

| 新类落在哪一层 | 数量 |
|---|---:|
| E3xxx 语法（`unexpected token`） | 12 |
| E4xxx 类型轴（无此方法/无此 trait/类型不匹配） | 9 |
| E4021 改名导致的未绑定标识符 | 3 |
| 其他 | 5 |

**四成是纯语法破坏**，还有一成是"把变量名改了导致未绑定"。它更像一把
"语法破坏多样性尺"，不是类型深度尺。剩下的 9 个类型轴类倒是有价值
（`Bytes does not implement Sub`、`String has no method to_json`），
但它们是**错误路径**，没有把编译推到新的 monomorphization。见
`real_corpus.md` §2.1：同一批变异体的函数覆盖严格 ⊆ 种子。

## 怎么用（还没接进主循环）

* 作为"保留策略"时要限定 **只看 E4xxx 且排除 E4021**，否则会被语法噪声刷屏；
* 作为 corpus minimization 的第二目标（边并集 + 诊断类并集双向压缩）；
* 作为回归指标：`diag.py --out baseline.json` 存档，代码更新后比较"类是否丢失"
  （丢失 = 诊断质量回归，比边覆盖回归更早报警）。

## 局限

1. 归一化是启发式的：`<loc>`/`<n>`/引号截断都可能把两个不同的类合并；
2. 保留类型名会放大类数（一个泛型实例化差异就是一个新类），做趋势可以，
   做绝对值没有意义；
3. 诊断类多 ≠ 缺陷多：E3002 parse error 的类很多，但它只是"变异把语法弄坏了"。
   所以它衡量的是**探索深度**，不是缺陷密度。
