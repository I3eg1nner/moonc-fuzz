# 真程序语料（A 层）：用 core 自己的代码喂 moonc

日期 2026-11-11。目的：回答"玩具片段到 18% 就上不去了，换成真实程序能到哪"。

## 1. 语料来源与编译模型

`~/.moon/lib/core` 自带完整源码：**1,473 个 `.mbt` / 141 个包 / 33.1 万行**，
外加 130 个已编译好的 `.mi`（`_build/wasm-gc/release/bundle`）。

编译模型（`harness/realcorpus.py`）：

```
moonc build-package <file> -o out.core -pkg fuzz/p -pkg-type library \
      -target wasm-gc -g -O0 -workspace-path . \
      -i <bundle>/<pkg>/<pkg>.mi:<短别名>   × 130
```

三个必须踩过的坑：

1. **`-i` 的别名必须是短名**。写 `.../array.mi:moonbitlang/core/array` 时
   `@array` 解析不了（E4037 "package array is not imported"）；写 `:array` 才行。
   这就是"依赖全给、代码仍然不认识包"的原因。
2. **`-pkg-type` 的取值是 `library` / `executable` / `foreign_library`**，
   没有 `lib`；给错会直接 usage 退出（rc=2、无 E 码）。
3. core 里 `archive/zip`、`async/*`、`compress/*` 是**子包**，`all_pkgs.json` 里
   rel 带 `/`，用 basename 当别名即可（本仓 130 个 .mi 按别名去重后无冲突）。

## 2. 可运行率（这是 A 层的第一个指标）

| 单元 | 成功/总数 | 可运行率 |
|---|---:|---:|
| 单个 `.mbt`（library 包） | 662 / 1,473 | **44.9%** |
| 整包（目录内全部 `.mbt`） | 74 / 141 | **52.5%** |
| 体变异 gen0（真程序为种子） | 215 / 300 | **71.7%** |
| 体变异 gen1（成功变异体再当种子） | 226 / 300 | **75.3%** |

失败原因（单文件模式）几乎全是 **E4021 / E4024（未绑定名字/类型）**：
core 的 `*_test.mbt` 是**白盒测试**，会引用同包私有符号，而私有符号不在 `.mi` 里。
要消掉这类失败只能按"整包"编译（第二行），这也解释了 52.5% 的天花板——剩下
的包要么跨包依赖没进 bundle（async/js 专属），要么需要 `test` 专用编译模式。

对比：模板流水线的可运行率是 71.8%，**体变异的 71.7% 说明"接受型变异"可以
原样搬到真程序上**，而且是 624 个真实程序当种子，不是 25 个模板。

### 2.1 但变异对覆盖是**空操作**（2026-11-11 决定性实验）

可运行率高只说明"没把程序弄坏"，不说明"把编译器推进了新地方"。直接测函数增量
（`cov.py funcs --real`，同调用，`Moonc.*`）：

| 语料 | n | 并集 `Moonc.*` | 每输入均值 | 相对种子新增 |
|---|---:|---:|---:|---:|
| 种子（624 个真程序） | 624 | **5,289** | 1,217 | — |
| gen0（体变异一代） | 218 | 4,636 | 1,134 | **0** |
| gen1（自举二代） | 244 | 3,904 | 1,041 | **0** |

三条事实：

1. **gen0 − seeds = 0，gen1 − seeds = 0**：变异体命中的函数**全部**是种子已经覆盖的；
2. **gen1 − gen0 = 0，且并集从 4,636 掉到 3,904（−16%）**：自举不是在加深，是在收窄；
3. 每输入均值 1,217 → 1,134 → 1,041：**每代都更浅**。

结论：**"变异策略错配"被证实，而且它同时也不是约束**——变异的作用面在语法/文本层，
其函数覆盖严格 ⊆ 种子。71.7% 的可运行率买不到任何新函数。

## 3. 深度：每个输入打进去多少

单进程内 AFL QEMU 的边 id 是顺序分配的（见 §5），所以**单输入的边数**是精确的：

| 指标 | 值（n=1,368 次真实编译） |
|---|---:|
| 平均 TB 边 | 26,471 |
| 中位数 | 26,230 |
| p90 | 35,558 |
| 最大 | 47,109 |

即：一次真程序编译平均触发的 TB 边数 ≈ 2.6 万，和单模板（2.5 万）同量级——
**真实程序带来的是"类型正确性"和"语义多样性"，不是单次边数**。

### 3.1 函数覆盖（A 层的结论数字，2026-11-11 修订）

**旧数字作废**：之前写"18.0% → 21.5%"是把"换语料"和"换编译调用"混在一起了。
旧语料用的是 `wasm + executable + 2 个 .mi`，真程序用的是
`wasm-gc + library + 130 个 .mi`。固定调用后重测（全部改成新调用）：

| 语料 | 调用 | n | `Moonc.*` / 26,611 |
|---|---|---:|---:|
| 旧混合语料 | 旧（wasm/executable/2 mi） | 232 | 4,643（17.4%） |
| 旧混合语料 | **新（wasm-gc/library/130 mi）** | 232 | **5,080（19.1%）** |
| core 真程序 | 新 | 1,368 | **5,734（21.5%）** |
| **两批并集** | 新 | 1,232 | **5,925（22.3%）** |

**真正的语料效应 = +654 个函数（+2.5pp）**，其中 437 个来自调用差异本身。
并集里真程序独有 845 个、旧语料独有 191 个 ⇒ **两批高度互补，最优数字是 22.3%**
（上一版报 21.5%，等于把自己的最优数字说低了）。

### 3.2 "加输入还有没有用"：用贪心序重画（修订）

之前用 `per_input_new` 中位数 0 论证饱和，这是错的：那条曲线是按"文件大小升序
+ 等步采样"排的，前 100 个全是几行的小文件（很多根本编译不过），所以曲线形状
是**排序造成的假象**，不能当饱和证据。

用 `harness/order.py` 重画（函数级并集，单位：函数数）：

| 序 | n=100 | n=232 | n=500 | n=1000 | n=1368 |
|---|---:|---:|---:|---:|---:|
| path（旧口径） | 2,180 | 3,877 | 4,885 | 5,485 | 5,734 |
| size_asc | 738 | 2,486 | 3,599 | 4,962 | 5,734 |
| size_desc | **5,382** | 5,537 | 5,650 | 5,681 | 5,734 |
| rand ×3 | 4,598 / 4,569 / 4,633 | ~5,000 | ~5,330 | ~5,630 | 5,734 |
| pkg_round_robin | 5,382 | 5,537 | 5,650 | 5,681 | 5,734 |
| **greedy（上界）** | **5,700** | **5,734** | 5,734 | 5,734 | 5,734 |

读法：

1. **path 序的"后 868 个只多 251"是排序假象**，撤回；随机序下 n=232 已经是 5,000+。
2. **并集本身在 ~5,734 处就平了**：贪心序 **232 个输入就覆盖全部**，
   随机序 1,000 个到 5,693（99.3%）。所以"再加核心文件"的结论仍然成立，
   但证据是**并集饱和**，不是"边际中位数 0"。
3. 这只说明**core 这一批语料内部同质**，不说明"编译器可达空间见底"——
   `E*` 依然未知。

## 4. 分阶段：墙在 frontend 还是 backend（C 层，修订）

同一批 60 个真程序，只换子命令：

| 阶段 | 命中 `Moonc.*` | 执行 TB 总数 | 说明 |
|---|---:|---:|---|
| `check` | 3,116 | 68,366,363 | parse+typer+生成 .mi |
| `build-package` | 3,669 | 71,477,216 | +monofy+core IR+wasm-gc codegen |

**函数计数不是工作量**：函数数是 3,116 vs 3,669（85%），但**执行 TB 数只差 4.6%**
（68.4M vs 71.5M）。按工作量算，**95.6% 的工作在 `check` 里**，后端只是薄薄一层。
两个指标方向一致，但"85%"是下界，按工作量说更接近 96%。

另外补了两个对照，排除"是编译模型/目标压低了深度"：

| 对照 | 结果 |
|---|---|
| 同 200 文件，四种 target | wasm-gc 4,599 / wasm 4,640 / js 4,622 / native 4,633（**极差 0.9%**） |
| 整包编译（141 个包，依赖完整）vs 单文件（1,368） | 5,753（21.6%）vs 5,734（21.5%）**≈ 相同** |

所以"单文件模型"和"wasm-gc 目标"都不是限制因素。但要说清楚：**"墙在 typer"目前
仍是假设**——`E*` 未知，我们能说的只是"可达代码里 96% 的工作在前端，而前端没被
喂到新的类型组合"。要证伪它，得做出真正改变类型组合的输入（`.mbti` oracle），
而不是继续换语料来源。

## 5. 口径修正（F 层）：之前报的"边覆盖率"作废

用 `--dump-slots` 落盘后可以直接验证 id 的性质：

* 默认 QEMU 模式的 union_slots = **{5, 6, …, N} 连续区间**（实测
  `max−min+1 == len`），因为 `afl_idtable_lookup` 的 id 是
  `next_id % (map_size−5) + 5`，**按翻译顺序递增**。
  ⇒ 跨进程并集没有意义（并集 = 最大单输入的 N），之前报的
  "T1 52.2% / T2 75.2% 边覆盖"**作废**。
* 只有 `AFL_QEMU_OLD_COVERAGE=1` 的 `hash(pc) ^ (prev>>1)` 跨进程稳定，
  但 16 位哈希在高密度下有碰撞：本语料实测 50,388 个不同槽位，
  按生日校正反推真实边数 ≈ **9.6 万**（±，仅作量级参考）。

因此**跨语料比较只用函数覆盖**（nm 符号化，无哈希、无碰撞、分母明确），
边数只在"单输入/单进程"意义下引用。

每输入槽位已落盘：`out/slots_realcore/`（1,368 个 `.slots` + `_manifest.jsonl`，
196 MB），以后算并集/最小化不用重跑。

## 6. 词典（E 层）：有效，但方向要对

`harness/mkdict.py` 从 130 个 `.mbti` 抽出 **1,177 个 token**（45 关键字、
36 运算符、1,119 个出现 ≥2 次的 API/类型名）。

A/B（400 次采样，真程序当种子，`moonc syncheck` 为判据）：

| 变异方式 | parse 成功率 |
|---|---:|
| 无词典（基线） | 36.2% |
| **插入**词典 token 到随机边界 | **30.5%（变差）** |
| 用词典标识符**替换**一个标识符 | **85.8%** |
| 用关键字/内建类型替换 | 78.5% |

结论：**插入是负收益**（在 token 边界硬插必然破坏语法），替换是正收益。
但替换也不是"可运行率越高越好"——T2 编译成功率反而从 23.7% 降到 18.7%，
因为它把局部变量换成了 core 的 API 名（未导入 ⇒ 类型错误）。
词典真正的价值是**命名/类型入口的多样性**（能撞到新的 typer 分支），
不是可运行率。`m_dict_token` 已按"替换式"实现（`harness/mutate.py`）。

## 7. 复现

```bash
# 单文件可运行率 + 语料落盘
python3 harness/realcorpus.py harvest x --src ~/.moon/lib/core \
        --out seeds_real --json out/real_core_compile.json --workers 64
# 整包
python3 harness/realcorpus.py pkgs x --src ~/.moon/lib/core \
        --json out/real_core_pkgs.json --workers 32
# 体变异自举（2 代）
python3 harness/realcorpus.py bootstrap seeds_real --out out/boot_real --limit 300
# 覆盖率（真程序模式；check/build 分阶段）
python3 harness/cov.py funcs seeds_real --limit 60 --real --stage check --out out/cov_real_check60.json
python3 harness/cov.py funcs seeds_real --limit 60 --real --stage build --out out/cov_real_build60.json
# 词典
python3 harness/mkdict.py harness/moonbit.dict
```
